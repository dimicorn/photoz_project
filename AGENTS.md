# AGENTS.md — photo-z методом kNN: репрезентативная и смещённая выборки

## 0. Цель и образ результата

Проект изучает, как качество photo-z методом k ближайших соседей, обученного на
Happy A, зависит от того, насколько проверочная выборка похожа на обучающую.
Пользователь ставит задачи сообщениями в сессии (раздел 8). После каждого
сообщения в проекте существуют:
- результат задачи — то, что требует её «Готово, когда»;
- заметки задачи в `tasks/` с актуальным статусом и итогом;
- заметки объектов работы в `notes/` по онтологии `ontology.yaml`;
- запись в `diary.md`.

Расчёт photo-z — `src/photoz.py` (`.venv/bin/python -m src.photoz`): пишет
`results/predictions_<X>.csv` (`id, z_spec, z_phot`, строки в порядке файла данных)
и `results/metrics.csv` (`sample, n, k, bias, sigma_nmad, outlier_frac`).

### Чего агент не может знать сам

- Признаки — `feat1..feat5`: величина и цвета, уже стандартизованные по Happy A.
  k = 10, евклидово расстояние, photo-z — среднее `z_spec` соседей.
- Метрики по `dz = (z_phot − z_spec)/(1 + z_spec)`: `bias` — медиана dz;
  `sigma_nmad` = 1,4826·медиана|dz − медиана dz|; `outlier_frac` — доля |dz| > 0,15.
- В статье (с. 9, 15) bias — среднее, оценщик colors-kNN-z — медиана 11
  соседей, манхэттенская метрика. Числа статьи с нашими напрямую не сравнивать.
- Обучать только на Happy A. B, C, D — проверочные: обучение на них — утечка.
- Ожидаемо σ_NMAD на B ≈ 0,02; вне 0,01–0,08 — остановиться и сообщить.

## 5. Протокол работы

1. Прочитать `STATUS.md`, `INDEX.md` и заметки `tasks/` (статусы).
2. Сообщение принимает результат или просит переделать — сменить статусы (8.3).
3. Сообщение ставит работу — записать задачу до расчётов (8.2), показать план.
4. Работа в режиме ReAct: изменить скрипт, запустить, проверить; заметки объектов —
   по ходу (8.1). Затем статус «выполнена» и итог.
5. Критерий раздела 1; `diary.md`; перезаписать `STATUS.md`; ответ пользователю.

## 6. Память

## 8. Граф проекта

Хранилище Obsidian — корень проекта; заметки классов `ontology/` уже созданы.
Заметки пиши **одной командой**, а не по файлу: составь YAML по образцу в начале

`.venv/bin/python -m src.graph status "tasks/<имя>.md" <статус> --itog "<текст>"`.

### 8.1. Заметки объектов

- `notes/<название>.md`; тип — класс из `ontology.yaml`; связи — только его
  отношения, от области определения к области значений, в заметке-источнике связи.
- Название — экземпляр, не класс: «Выборка Happy C», «σ_NMAD на Happy C 0,0xxx».
  Без символов `/ \ : # | [ ]`. Цель связи с запятой в YAML — в кавычках.
- Файлы — ссылкой по пути от корня: `data/raw/happy_C.txt`, `src/photoz.py`.
- Уже есть: выборки A, B, C, D; метод, метрики, гипотеза, эксперименты по B/D и C, их
  результаты и проверки, ограничения, источник `Ashmead 2026`. Ссылайся на них, не
  дублируй.
- Эксперимент: `решает` задачу, `проверяет` гипотезу, `обучаетсяНа`, `оцениваетсяНа`,
  `применяет`, `даёт`, `реализованВ`. Результат: `выраженВ`, `подтверждает` или
  `опровергает`, `проверенЧерез`, `хранитсяВ`.
- Отчёт — сам файл `reports/<название>.md` с `type: Отчёт`: `выполняет` задачу,
  `описывает`, `ссылаетсяНа` источник; утверждение из источника — со ссылкой [[Ashmead 2026]].
- Объекта нет в онтологии — строка «Новый тип: <почему>»; `ontology.yaml` не менять.

### 8.2. Задачи

- `tasks/<действие>.md`, `type: Задача`, `status: открыта`; в тексте — «Запрос
  пользователя: «<дословно>»», «Готово, когда: <файл, число или команда>», «Не входит: …».
- Подзадачи — только если нужны, 2–4, связью `подзадачаОт`.
- Статусы: открыта → в работе → выполнена (с разделом «Итог»: что сделано, чем
  проверено) или заблокирована; «принята» — только по словам пользователя.

### 8.3. Приёмка

«Принимаю» (или равное по смыслу) — статус «принята», в итог строка «Принято
пользователем: «<его слова>»». Просьба переделать — «в работе».
